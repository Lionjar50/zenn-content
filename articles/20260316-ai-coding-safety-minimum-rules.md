## はじめに

2026年に入って、AIコーディングツールは「便利なお試し枠」を超えました。

- Claude Code
- Codex
- Cursor
- MCP対応エージェント

このあたりを触っていると、**もう日常業務に入れた方が速い** という場面が増えています。

一方で、現場で使い始めるとすぐにぶつかるのが、次の不安です。

- 機密ファイルを勝手に読まれないか
- 危ないコマンドを実行しないか
- dependency を雑に更新して壊さないか
- 生成結果をそのまま信じて事故らないか

今のトレンドを見ても、単なる「速い」「便利」だけでは弱く、**どう安全に回すか** まで含めて語られる記事の価値が上がっています。

この記事では、個人開発〜小規模チームでAIコーディングを導入する時に、**最低限これだけはやった方がよい** という実務ルールを整理します。

---

## 結論

先に結論を書くと、最低限必要なのはこの5つです。

1. **読ませてよい範囲を決める**
2. **実行してよいコマンドを絞る**
3. **AIの提案と実行を分ける**
4. **依存関係更新と本番系変更は別扱いにする**
5. **ログと差分を必ず人間が確認する**

AIコーディングで事故る時は、だいたい「モデルが賢くないから」ではなく、**境界が曖昧なまま権限を渡したから** 起きます。

---

## 1. 読ませてよい範囲を決める

まず最初にやるべきなのは、**何を読ませてよくて、何を読ませないか** の線引きです。

特に危ないのは次のようなものです。

- `.env`
- APIキーやトークンを含む設定ファイル
- 本番接続先情報
- 顧客データ
- 認証Cookieやセッション情報

「ローカルにあるものは全部読める」状態のまま使い始めると、便利さより先に事故率が上がります。

### ルール

- プロジェクトごとに **読ませないファイル** を先に定義する
- secrets は可能なら **別ディレクトリ** に逃がす
- `.claudeignore` や類似の ignore 設定を活用する
- 「AIに読ませる前提の情報」と「人間だけが触る情報」を分離する

### 実務感

ここを先にやるだけで、かなり安心して使えます。逆に言うと、これをやらずにツール比較をしてもあまり意味がありません。

---

## 2. 実行してよいコマンドを絞る

次に重要なのは、**AIに何を実行させてよいか** です。

危険なのは、次のような操作です。

- `rm -rf`
- 本番系への直接デプロイ
- 権限変更
- 破壊的な migration
- 広範囲な package update
- 外部公開を伴う操作

AIは悪意がなくても、状況を誤読して**強すぎるコマンド** を出すことがあります。

### ルール

- AIにはまず **read / diff / test** を優先させる
- 書き込みより前に **提案だけさせる** ことを増やす
- 破壊的操作は **都度承認** にする
- 本番・公開・課金を伴う操作は **人間専用** にする

### 目安

AIに任せやすいもの:
- 調査
- リファクタ
- テスト追加
- ドキュメント更新
- ローカル修正

人間が握るべきもの:
- deploy
- billing
- secrets
- production migration
- 外部送信

---

## 3. AIの提案と実行を分ける

ここはかなり重要です。

AIコーディングを安全に回したいなら、
**「考える役」と「確定する役」を分ける** 方が安定します。

たとえば、いきなり

> この不具合を直してそのまま反映して

よりも、

> 原因を特定して、修正案を出して、差分を見せて

の方が安全です。

### おすすめの流れ

1. 原因調査
2. 修正案提示
3. 差分確認
4. テスト実行
5. 人間承認
6. 反映

この順にするだけで、AIの暴走というより、**人間の見落とし** をかなり減らせます。

---

## 4. dependency 更新と本番変更は別扱いにする

AIに任せて地味に危ないのが、dependency 周りです。

例:
- パッケージをまとめて更新
- lockfile を大量変更
- indirect dependency が増える
- いつの間にか major 更新が混ざる

これを通常のコード修正と同じノリでやると危険です。

### ルール

- dependency更新は **単独PR / 単独差分** に分ける
- まとめて上げず、**小さく刻む**
- `npm audit fix --force` 的なものは自動実行させない
- 変更理由をAIに説明させる

### 本番変更も同様

- infra変更
- CI/CD変更
- 権限変更

は、**アプリコードの修正と分ける** のが安全です。

---

## 5. ログと差分を必ず人間が確認する

AIコーディングで一番危ないのは、
**うまくいったように見えて、実はよく見ていない** 状態です。

なので最低限、次は必須です。

- 実行ログを見る
- diff を見る
- テスト結果を見る
- 想定外ファイルが触られていないか確認する

### 実務的には

レビュー時に見るポイントはこの4つで十分です。

- どのファイルを触ったか
- 変更量は妥当か
- 危険な設定に触れていないか
- エラーを握りつぶしていないか

「全部読む」のではなく、**事故りやすい場所だけ重点確認** で十分回ります。

---

## 6. 個人開発とチーム運用で分けて考える

ここも重要です。

### 個人開発

個人開発なら、かなり攻めても回せます。

- ローカルでの修正は広めに許可
- テスト生成も積極活用
- ドキュメント整備もAIに任せやすい

ただし、本番・課金・外部公開だけは分離した方が良いです。

### チーム運用

チームでは、便利さより先に**再現性**が必要です。

そのため、
- 権限設計
- レビュー基準
- AI利用範囲
- 禁止操作

を短くてもよいのでルール化した方がいいです。

「各自の感覚で使う」は、短期では速くても長期では崩れやすいです。

---

## 7. 最低限の運用テンプレート

もしこれから導入するなら、最初はこのくらいで十分です。

### AIコーディング最低限ルール

- secrets を含むファイルは読ませない
- AIはまず提案、いきなり確定しない
- destructive command は人間承認
- dependency 更新は単独で扱う
- 本番変更はAI単独でやらない
- diff / test / log を人間が確認する

この6行だけでも、現場の安定感はかなり変わります。

---

## 8. ツール比較より先に、運用設計が必要

今は Claude Code、Codex、Cursor、MCP など、ツール比較の話題が強いです。

もちろん比較自体は大事ですが、実務で差が出るのは、
**どのツールを選んだか以上に、どう運用設計したか** です。

- どこまで読ませるか
- 何を実行させるか
- どこで人間レビューを入れるか
- 何を禁止するか

この設計があると、ツールを変えても崩れません。

逆にここがないと、どのツールを選んでも事故ります。

---

## まとめ

AIコーディングを速くしつつ事故らないために、最低限必要なのは次の5つです。

- **読ませてよい範囲を決める**
- **実行してよいコマンドを絞る**
- **AIの提案と実行を分ける**
- **dependency 更新と本番変更を別扱いにする**
- **ログと差分を人間が確認する**

2026年のAIコーディングは、もう「使うか使わないか」ではなく、
**どう安全に組み込むか** のフェーズに入っていると思います。

速さだけを追うより、事故らず継続できる形を先に作る。結局それが一番速いです。
