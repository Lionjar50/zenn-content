AIエージェントを常時運用すると、最初に詰まるのはモデル性能ではありません。
実際には **「本当に止まったのか」「誤検知なのか」「誰が再起動するのか」** の設計が先に問題になります。

今回は、OpenClaw を常時運用する中で実際に起きた **watchdog の誤検知 → 5分おき再起動** という事故と、その直し方をまとめます。

派手な話ではありません。
ただ、AIエージェントを仕事で回すなら、この手の地味な運用設計のほうがモデル比較より先に効きます。

---

## 何が起きたか

ある日、`OpenClaw daemon is NOT running` という通知が定期的に飛ぶようになりました。
最初は「gateway が不安定になったのか」と思ったのですが、実際にログを見ると少し様子が違いました。

- 00:30 に SIGTERM
- 00:35 に SIGTERM
- 00:40 に SIGTERM
- 00:45 に SIGTERM
- 以後、ほぼ 5 分おきに同じ挙動

しかも launchd の KeepAlive が効いていたので、完全停止ではなく **落とされては即復帰** を繰り返していました。

つまり、自然クラッシュではなく、**どこかが定期的に終了シグナルを送っている** という状況でした。

---

## 原因は watchdog 側だった

調べてみると、原因は OpenClaw 本体ではなく、別で動かしていた watchdog スクリプトでした。

watchdog は 5 分おきに動いて、OpenClaw が生きているか確認し、止まっていれば再起動する構成にしていました。

ただ、ここで使っていた判定が問題でした。

```bash
pgrep -x "openclaw"
pgrep -f "entry.js gateway"
```

この判定は、現行の gateway プロセス名と一致していませんでした。
その結果、**OpenClaw は生きているのに「死んでいる」と誤判定** していたわけです。

そして watchdog は親切に再起動処理を実行します。
この「親切」が 5 分おきに発動したことで、**watchdog 自身が障害を作る側** になっていました。

ここで痛かったのは、通知だけ見ると「OpenClaw が不安定」に見えることです。
でも実態は逆で、**監視のほうが壊れていた** という構図でした。

---

## どう直したか

修正方針は単純で、**プロセス名判定をやめて、サービスの疎通を直接見る** ようにしました。

OpenClaw にはローカルの health 確認に使える endpoint があるので、watchdog の判定をこれに寄せました。

```bash
curl -sf --max-time 3 http://127.0.0.1:18789/
```

これで見ているのは「その名前のプロセスがいるか」ではなく、**実際に gateway が応答できるか** です。

さらに再起動処理も少し分けました。

- service が loaded / running ですらない → bootstrap
- service は loaded だが応答しない → kickstart

つまり、
**launchd の状態確認** と **アプリケーションの health 確認** を分離しました。

この分離を入れるだけで、監視の見え方がかなり変わります。

---

## 修正後どうなったか

修正後に `watchdog.log` を確認すると、直近は以下のように並びました。

- `OK - all services healthy`
- `OK - all services healthy`
- `OK - all services healthy`

少なくとも再修正後の監視では、5 分おき誤再起動の再発は見えていません。

ここでようやく、「OpenClaw が落ちていた」のではなく、**watchdog が誤って落としていた** と確定できました。

---

## ここで学んだこと

今回の件で一番大きかった学びは、監視は「プロセス名」ではなく **サービス疎通** を見るべきだということです。

理由は単純で、プロセス名は変わります。
構成変更、ラッパー、実行方法の差分で、簡単にズレます。

一方で「実際に応答できるか」は、監視したい本質に近いです。

そしてもう1つ大事だったのは、**誤検知は停止より危険なことがある** という点です。

停止なら分かりやすいです。
でも誤検知は、

- 正常系を壊す
- 通知を汚す
- 原因切り分けを難しくする
- 人間側に「本当に危ない通知」を見落とさせる

という形で効いてきます。

監視は安全装置のつもりで入れがちですが、設計が甘いと普通に障害源になります。

---

## cron / heartbeat / watchdog を混ぜない

AIエージェント運用で地味に大事だったのが、定期処理の役割分担でした。

自分の中では今のところ、こんな分け方が一番安定しています。

| 役割 | 何をするか |
|---|---|
| cron | 正確な時刻に実行したい処理 |
| heartbeat | 文脈を見ながらの定期確認 |
| watchdog | 生きているかの最低限チェック |

これを混ぜると、かなり危ないです。

たとえば watchdog が「ついでに再起動も通知も状態整理も全部やる」構成になると、判定ミス 1 回で影響範囲が一気に広がります。

逆に役割を分けておくと、どこで壊れたかを切り分けやすくなります。

AIエージェントを実運用するなら、モデル選定と同じくらい、**周辺の定期処理をどう分離するか** が効きます。

---

## そのまま使える考え方

もし AI エージェントを自宅や社内で常時運用するなら、最低限この順番で見るのがおすすめです。

1. **監視対象はプロセス名ではなく疎通で見られるか**
2. **loaded / running と health check を分離できるか**
3. **再起動処理は本当に必要なときだけ走るか**
4. **通知は誤検知を増やさない形になっているか**
5. **「異常時だけ知らせる」設計になっているか**

派手な最適化ではありませんが、この順番を押さえるだけでかなり安定します。

---

## まとめ

AIエージェントを実運用して分かったのは、最初に問題になるのは性能ではなく **監視設計** だということでした。

今回の件も、OpenClaw 本体の不安定化ではなく、watchdog の誤検知が原因でした。
そして直したポイントはとても地味で、**プロセス名判定をやめて health endpoint を見る** ことです。

AI の本体性能はもちろん大事です。
ただ、実際に毎日回す段階に入ると、効いてくるのはもっと泥臭い部分です。

- どう監視するか
- 誰が再起動するか
- どこで止めるか
- 誤検知をどう減らすか

このあたりを先に整えるだけで、運用の安心感はかなり変わります。

もし今、AIエージェントを「試す」から「回す」に移そうとしているなら、
モデル比較より先に **watchdog を疑ってみる** くらいでちょうどいいかもしれません。
